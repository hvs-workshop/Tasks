# Shai Hulud Workshop

> **Scope:** This workshop recreates the *mechanisms* behind software-supply-chain attacks in isolated, authorized training environments. Use test accounts, a dedicated workshop repository, synthetic credentials, and disposable runners. Never collect real secrets, upload other people's data, or run arbitrary issue text as a shell command.


## Learning objectives

By the end of the workshop, you should be able to:

1. Explain how a trusted editor/dependency execution path can start a multi-stage chain.
2. Recognize when a pull-request workflow crosses a GitHub Actions trust boundary.
3. Understand how a self-hosted runner can receive work from GitHub events — and how to restrict that mechanism.
4. Describe appropriate detection, containment, and cleanup steps.

# [Bonus] Task 3: GitHub Actions Runner as C2 

**Goal:** Connect a temporary Debian WSL instance as a GitHub Actions self-hosted runner. Use the body of an issue as a **command channel**, while ensuring that **only the repository owner can trigger the demo**.

## 1. Create a private repository

1. Sign in to GitHub.
2. Create a **new private** repository named `issue-runner-lab` under your own user account.
3. Do not add collaborators for this exercise.
4. Ensure **Settings → General → Features → Issues** is enabled, and enable GitHub Actions if required by policy.
5. Use **no real repository secrets** in this lab.

## 2. Enter your Debian WSL

If you have closed your Debian WSL container from exercise 1, execute

```
wsl -d Debian
```


## 3a. (Recommended) Register your self-hosted runner

1. Navigate to your private repository on GitHub.
2. Open **Settings → Actions → Runners → New self-hosted runner**.
3. Select **Linux** and the matching system architecture (x64)
4. Follow Instructions

## 3b. (Alternative Path) Register your self-hosted runner with GH Token

The actual Shai Hulud worm did not use manual clicks, but instead performed all actions via API.

> We would strongly advise you to use a LLM of your choice to assist you

1. Create a GitHub PAT that has the `Administration: Read & write` permission. 
2. Get the registration token from `https://api.github.com/repos/OWNER/REPO/actions/runners/registration-token`
3. Connect runner to token `./config.sh --url https://github.com/OWNER/REPO --token "$REG_TOKEN" --name "my-custom-runner" --unattended && ./run.sh`

## 4. Add an owner-restricted issue workflow

In your private repository, create `.github/workflows/issue-demo.yml` with the following minimal example. It reads the issue body **as data**, checks both the issue creator and the actor who triggered the event, and supports only three fixed diagnostic requests.

```yaml
name: Owner-only issue instruction demo

on:
  issues:
    types: [opened, edited]

permissions: {}

jobs:
  demo:
    # Both the author of the issue and the user generating the event must own the repo.
    if: >-
      ${{ github.event.issue.user.login == github.repository_owner &&
          github.actor == github.repository_owner }}
    runs-on: [self-hosted, linux]
    timeout-minutes: 2
    env:
      # Treat issue-body text strictly as data, never as shell source code.
      REQUEST: ${{ github.event.issue.body }}
    steps:
      - name: Handle a fixed set of harmless requests
        shell: bash
        run: |
          case "$REQUEST" in
            'workshop: status')
              printf 'Workshop runner is responding.\n'
              ;;
            'workshop: time')
              date -u '+%Y-%m-%dT%H:%M:%SZ'
              ;;
            'workshop: platform')
              uname -s
              ;;
            *)
              printf 'Request ignored: not on the allowlist.\n'
              ;;
          esac
```
